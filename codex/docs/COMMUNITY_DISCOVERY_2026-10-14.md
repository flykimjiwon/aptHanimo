# 한바퀴 · 주민 이야기 탐색과 개선 모아보기

2026-10-14 후속 개발. 기본 `/`의 **동네 수첩 → 주민 이야기**에서 사용한다. 단지 섬·지도 원자료·이전 앱은 유지한다. 접수·사진 처리·검토 명령·저장 설정은 [모바일·주민 제보 운영 가이드](COMMUNITY_MOBILE_2026-10-14.md)를 따른다.

## 사용자 흐름

- **사진 요청**: 아직 반영 완료되지 않은 공개 사진 요청만 모은다.
- **개선 제안**: 공개 중인 지도·성능 개선 글만 모은다.
- **반영 완료**: 운영자가 완료 상태로 바꾼 공개 글과 처리 설명·업데이트 날짜를 본다.
- **종류·주제·상태 고르기**: 세 조건을 함께 적용한다. 예: 지도·성능 개선 + 속도·조작 + 공개 중.
- 조건 초기화, 새로 불러오기, 20건씩 이전 이야기 더 보기. 필터는 같은 단지의 수첩을 닫았다 열어도 유지하며 새로고침·단지 교체 때 초기화한다.

숫자는 해당 단지의 공개 자료만 집계한다. 요청·제안 숫자는 `published`, 완료 숫자는 모든 종류의 `resolved`다. 이 세 숫자의 합은 전체 글 수가 아니다. 필터 결과의 총 건수는 별도로 표시한다. 검토 대기·비공개 글과 다른 단지 자료는 목록·숫자 모두에서 제외한다. 공개 상태는 사실·실거주 인증이나 담당자 배정을 뜻하지 않는다.

## 조회 계약

```text
GET /api/community/posts?complex=xi&kind=request&topic=map&status=published
```

| 항목 | 값 |
|---|---|
| complex | xi / haiver / cherbo, 필수 |
| kind | all / positive / caution / correction / photo / request |
| topic | all / walk / transit / amenity / noise / map / performance |
| status | all / published / resolved |
| before | 이전 응답의 next. 생략 시 첫 페이지 |

세 필터는 생략하면 `all`. 잘못된 값·private 상태 요청은400. 기존 `posts`, `next` 응답에 `total`(필터 전체 건수), `progress: {requests, corrections, resolved}`(단지 전체 공개 집계)를 추가했다. SQL에서 필터링한 뒤 최신순20건을 선택하므로 첫20건 뒤에 있는 자료도 찾는다. 모든 값은 바인딩한다. 기존 DB 형식·접수증·쓰기 API는 변경하지 않았다.

필터 변경·새로고침은 이전 읽기 요청을 취소한다. 이전 응답은 새 조건이나 새 단지 화면을 덮어쓰지 않는다. 필터 DOM은 유지해 키보드 초점이 남고, 더 보기 성공 시 첫 추가 글 제목으로 초점을 옮긴다. 실패하면 기존 글·커서를 유지하고 버튼 바로 아래에 재시도 안내를 표시한다. 전체 조회 실패의 숫자는 `—`이며, 자료 없음의 `0건`과 구분한다. 자동 폴링은 없다.

**배포 시 프런트 빌드와 Bun 서버 재시작을 함께 적용한다.** 새 클라이언트는 집계 응답 필드가 필요하므로 과거 서버 프로세스에 새 정적 파일만 연결하면 조회 오류가 표시된다. DB 마이그레이션은 필요 없다.

## 이어서 할 일

1. 사진 요청에 답변 사진을 연결하는 후속 접수와 처리 이력. 현재는 요청과 사진이 독립 글이며 댓글·사진 답변 연결·담당자 배정·알림은 없다.
2. 본인 접수증 백업·동기화/계정 복구를 실제 참여 방식과 함께 정한다. 공개 필터에 비공개 접수 상태를 섞지 않는다.
3. 실제 iOS/Android·스크린리더·장시간 발열 검증과 주민 대상 사용성 평가.
4. 단지 원자료의 서비스 이용 권한, 영속 볼륨·HTTPS·백업 복원·운영 담당을 정한 뒤 외부 서비스 배포. Git 푸시와 로컬 확인을 인터넷 출시로 표현하지 않는다.
