근거가 있는 정보와 귀여운 연출을 구분하고, 월드·접속 광고로 무료 운영을 검증한다.

## 확정한 방향과 남겨 둔 확인
확정 방향은 단지 중심 생활권, 구별 허브, PC·모바일 웹, 1인·커플·가족, 네 가지 이동 방식, 검수한 정보와 무료 광고 모델이다. 실제 단지의 길·경사·시설·최신 이슈는 출처와 현장 확인 후 공개한다. 수입·일정·성능 숫자는 계획 가정이며 운영 실적이 아니다.
## 산출물의 현재 상태
기획서와 계약·가상 fixture·검증 도구를 완성했다. 실제 앱·서울 상세 월드·현장 실측·멀티플레이·광고망 계정은 아직 구현 또는 운영 검증을 수행한 상태가 아니다. 다른 세 AI 결과는 받은 파일만 통합 대상으로 삼는다.

# 1 제품의 목표
아파트 단지를 중심으로 주변 생활권을 귀여운 2.5D 월드에서 직접 돌아보는 무료 서비스를 만든다. PC 웹과 모바일 웹에서 사용하며 초·중·고·대학교, 직장, 역, 마트까지 생활 동선을 연결한다. 사용자는 혼자, 커플, 가족 단위로 입장하고, 걸어서 또는 유모차·자전거·자동차를 이용해 같은 장소를 서로 다르게 경험한다. 단지 외관을 구경하는 것에서 출발해 출근, 등하교, 장보기, 주차, 커뮤니티 이용 동선까지 비교하고 실제 임장 전에 확인할 질문을 얻는다.
핵심 결과물은 “우리 생활 방식으로 이 단지에서 살아보면 어떤가”에 답하는 체험이다. 월드 내부 광고와 접속·장면 전환 광고를 통해 운영비를 충당한다. 기본 탐색, 사실 확인, 불편 사항 열람, 단지 비교에 요금을 부과하지 않는다. 광고주가 사실 정보, 경로 계산, 평가 순위를 구매할 수 없도록 제품과 데이터 권한을 분리한다.
서울 25개 자치구 전체를 지역 선택 지도에 표시하고, 검수된 상세 월드를 1개 단지에서 3개, 이후 최소 구별 1개로 확장한다. 첫 화면의 지도 제공 범위와 실제 걸어 다닐 수 있는 상세 구현 범위를 각각 표시한다. 완성되지 않은 단지를 완성된 것처럼 보이게 하는 목업은 출시 범위에 포함하지 않는다.
이 문서는 제품 결정의 기준이다. 기술 구현은 02_ENGINEERING.md, 수집은 03_ASIDE_COLLECTION.md, 광고는 04_ADS_BUSINESS.md, 실행은 05_BUILD_PROMPTS.md, 네 AI 결과 통합은 06_MERGE_PROTOCOL.md를 따른다. 기계 판독용 계약은 packages/contracts에, 후보 단지는 data에 둔다. 근거 원장은 08_SOURCES.md이며 단독 전달 시에도 이 원장을 함께 제공한다. 본문에서 제안한 수치와 일정은 설계 가정이며 실제 성능·현장 측정·수입 실적과 구분한다.

# 3 사용자의 첫 체험
처음 방문하면 서울 지도와 상세 탐색 가능한 지역이 보인다. 로그인 없이 1인 체험을 시작할 수 있고, 저장이나 동행을 선택할 때 계정을 연결한다. 1분 안에 캐릭터를 움직이고 목적지 하나를 지정하도록 한다. 접속 광고는 수익화 단계에서 게임 시작 지점에 붙이며 첫 방문 학습을 방해하지 않는 빈도로 시험한다.
사용자는 “커플로 주말 임장”, “혼자 출근길 확인”, “아이와 유모차로 장보기” 중 하나를 고른다. 이것은 남녀 역할이나 가족 구성을 강요하는 선택지가 아니다. 각자의 관심사를 설정하는 프리셋이며 언제든 수정할 수 있다.
예를 들어 커플이 같은 동 앞에서 출발한다. 한 명은 역으로 가는 빠른 길을 선택하고 다른 한 명은 유모차 설정을 켠다. 계단이 있는 지름길과 경사로를 이용하는 우회로가 다르게 나타난다. 게임 속에서는 1분 정도 걸어도 현실 예상 시간은 별도로 표시된다. 두 사람은 “역은 가깝지만 유모차로는 이 출입구를 써야 한다”는 점을 함께 발견하고 메모한다.
이 예의 시간과 경로는 동작을 설명하기 위한 가상 상황이다. 실제 단지에 연결할 때는 출발 동, 출입구, 길이, 경사, 장애물, 확인 날짜가 있는 데이터로 치환한다.

PC에서는 월드가 화면의 중심이고 정보는 접거나 펼치는 서랍으로 제공한다. 모바일에서는 하단 이동 조작과 정보 패널이 겹치지 않게 한다. 건물이 캐릭터를 가리면 해당 건물만 반투명 처리하며, 지하층은 층 선택과 진입 애니메이션을 함께 사용한다. 한국어 라벨은 이미지에 구워 넣지 않고 UI로 표시한다.
# 5 귀여운 서울을 만드는 시각 규칙
## 외관과 지형
둥근 모서리, 부드러운 그림자, 작고 통통한 캐릭터, 무광 장난감 같은 재질을 기본으로 한다. 낡은 단지와 새 단지를 같은 품질로 매력 있게 표현한다. 구축은 바랜 외벽색, 창틀과 실외기, 오래 자란 나무, 작은 화단, 생활감 있는 벤치로 구별한다. 신축은 정돈된 조경, 넓은 출입구, 연결된 보행 공간, 커뮤니티 입구로 구별한다.
사용자가 원한 “살짝 금 간 귀여운 구축”은 가상 구축 테마에서 얇은 도장 갈라짐과 작은 보수 흔적으로 구현한다. 실제 단지에 구조 균열이나 누수·해충이 있다고 추정해서 텍스처를 붙이지 않는다. 연출 표시는 외관 스타일 정보에서 확인 가능하게 하고, 실제 하자 정보는 관찰 위치와 날짜가 검증된 별도 데이터로 다룬다.
지형의 언덕은 보이되 수치 계산에 과장된 높이를 사용하지 않는다. 카메라 때문에 경사가 잘 보이지 않으면 경사 띠, 고도 단면, 캐릭터 보행 속도 변화로 보완한다. 건물 높이를 시각적으로 줄였을 경우 거리 측정과 일조·조망 계산에는 사용하지 않는다. 초기 버전의 햇빛과 그림자는 분위기 연출이며 실제 일조 분석 기능이 아니다.
## 오브젝트와 캐릭터
공통 에셋은 아파트 동, 출입구, 보도, 계단, 경사로, 횡단보도, 담장, 옹벽, 놀이터, 지하철 입구, 엘리베이터, 주차 차단기, 광고판을 모듈로 만든다. 창문·수목·주차 차량은 인스턴싱으로 반복한다. 실제 브랜드 로고와 건물 사진을 그대로 복제하는 대신 권한이 있는 소재 또는 자체 제작물을 사용한다.
걷기에는 발걸음과 작은 그림자, 유모차에는 회전과 경사 이동, 자전거에는 타기·내려 끌기, 자동차에는 도로 추종·회전·주차 상태를 준다. 느린 길이 불편함을 느끼게 하되 반복 플레이를 막는 체력 소진이나 유료 회복은 넣지 않는다. 현실 거주민을 닮은 NPC를 만들거나 실제 거주 동·호수를 공개하지 않는다.
## 제작 자산의 기준
원본 모델과 재사용 에셋에는 제작자, 원본 파일, 사용 허가, 충돌체, 발밑 기준점, 실제 미터 치수, 렌더 축척을 기록한다. 자동 생성한 건물은 외관 초안이며 출입구와 보행 연결은 사람이 검수한다. 캐릭터와 소품의 그림체를 먼저 확정하고 단지별 장식을 추가해 제작 비용을 통제한다.
# 6 월드의 크기와 상세 수준
기본 제작 단위는 단지 중심 생활권이다. 서울 전체 지도는 구 선택과 지역 간 관계를 보여주고, 구별 허브는 단지를 고르는 역할을 한다. 단지를 선택하면 주변 학교·대학교·마트·역까지 연결된 상세 월드로 들어간다. 실내는 그 생활권에 연결된 별도 장면으로 제공한다.
단지 주변은 초기 수집 범위를 약 800m에서 1km로 잡되 반경을 경로의 강제 끝으로 쓰지 않는다. 실제 역 출입구·학교 정문·대학 캠퍼스 입구·마트 입구가 더 멀거나 우회로가 경계를 벗어나면 목적지까지 확장한다. 공간 데이터와 메시지를 구 단위 거대 파일 하나로 만들지 않고 장면과 청크 단위로 나눈다. 인접 단지의 생활권이 겹치면 보행로·시설·지형 청크를 공유해 중복 제작을 줄인다.
멀리 있는 대학교나 직장은 통근 요약과 목적지 장면으로 연결한다. 출발 단지에서 역까지, 대중교통 이동, 도착 역에서 캠퍼스·직장 입구까지를 각각 보여주며 중간 서울 전역을 고밀도로 제작하지 않는다. 시간표나 교통정보를 확보하지 못한 구간은 시나리오 추정 또는 미확인으로 표시한다. 개인이 입력한 직장·집 주소는 비공개로 관리한다.
| 공간 구성 | 이 제품에서의 역할 | 리소스 판단 |
|---|---|---|
| 서울 전역 연속 상세 월드 | 장기 확장 가능성 | 초기에는 필요하지 않은 공간까지 제작·검수할 부담이 큼 |
| 구별 허브 | 25구와 단지 선택 및 탐색 현황 | 가벼운 지도와 대표 장면으로 제공 |
| 단지 중심 생활권 | 실제 이동과 임장의 기본 공간 | 상세 제작을 필요한 경로·시설에 집중하는 권장안 |
| 원거리 목적지 연결 | 대학교·직장 통근 비교 | 이동 요약과 필요한 도착 장면을 단계적으로 연결 |

서울 지도의 장거리 이동은 지역 선택이나 지하철 이동으로 압축한다. 상세 동네에서는 길의 연결성과 고도, 출입 조건을 유지한다. 실제 길을 임의로 가까이 붙인 뒤 게임 좌표의 길이를 현실 거리로 계산하지 않는다.
| 상세 단계 | 공개하는 내용 | 완료 표시 |
|---|---|---|
| 후보 | 이름과 소속 구, 조사 목적 | 조사 후보 |
| 기본 정보 | 주소와 기본 현황, 출처 | 기본 정보 제공 |
| 외부 체험 | 검수한 단지·주변 동선 | 외부 탐색 가능 |
| 생활 체험 | 수단별 경로와 시설 정보 | 생활 동선 비교 가능 |
| 내부 체험 | 근거 있는 지하·커뮤니티 연결 | 내부 일부 탐색 가능 |

“내부 일부”는 체험 가능한 방 수와 정보 수준을 함께 보여준다. 모든 세대 내부나 모든 지하 공간을 복제했다는 의미로 사용하지 않는다.
# 7 이동 체험의 계산
## 경로의 출발점과 목적지
출발점은 단지 중심점 대신 선택한 동의 실제 출입구로 잡는다. 도착점도 역 이름의 좌표가 아니라 지상 출입구, 개찰구, 승강장 또는 목적 시설의 문으로 구분한다. 층이 다른 길이 평면상 교차해도 계단·램프·엘리베이터 연결 정보가 없으면 연결하지 않는다.
## 수단별 차이
| 수단 | 경로 조건 | 보여줄 체감 |
|---|---|---|
| 도보 | 통행 가능한 보행 링크, 계단과 경사 선택 | 걸음 거리, 오르막, 횡단보도, 외부 노출 구간 |
| 유모차 | 확인된 무계단 연결 우선, 턱·폭·엘리베이터 상태 반영 | 우회 거리, 연속 오르막, 좁은 길, 승강기 의존 |
| 자전거 | 실제 주행 허용 구간과 일방통행, 하차 구간 구분 | 경사, 끌기 거리, 거치 후 도보 |
| 자동차 | 도로 방향·회전·진출입 제한, 지하 진입 높이와 주차 권한 | 출차 경로, 병목 구간, 주차 후 동까지 이동 |

유모차가 계단을 자동 통과하거나 자전거가 모든 보도를 달리지 않게 한다. 자동차의 목적지는 실제 차량 출입구 또는 주차 지점이고, 거기서 사람의 보행으로 전환한다. 빠른 이동 버튼으로 게임 이동을 생략해도 현실 거리·시간·장애물은 그대로 남긴다.
수단별 속도 프리셋과 경사 페널티는 모델 가정으로 관리한다. 초기 예시로 도보 시속 4km, 유모차 3km를 사용할 수 있으나 실측 평균처럼 홍보하지 않는다. 자동차의 정체는 허가된 교통 데이터가 있을 때만 관측값으로 표시하고, 없으면 “평일 혼잡 가정”처럼 선택한 시나리오임을 표시한다.
## 시간과 불편의 표시
실제 예상 시간은 링크별 길이와 수단별 속도로 구한 이동 시간에 신호 대기, 승강기 대기, 주차, 수단 전환 시간을 더해 계산한다. 데이터가 없는 대기시간은 범위나 미확인으로 남긴다. 게임 재생 배속은 이 계산을 바꾸지 않는다. 물리적 사실과 이용자가 선택한 선호 비용을 별도로 저장해 개인별 우회 선호를 설명할 수 있게 한다.
“620m, 10~13분, 누적 상승 14m, 횡단 3회, 확인되지 않은 턱 1곳” 같은 카드는 표현 예시다. 초기 제품에서는 100점짜리 단지 순위보다 이처럼 해석 가능한 항목을 먼저 제공한다. 계단 수·급경사 구간·단절 보도·도로 횡단 횟수는 각각 확인된 값과 누락 범위를 함께 표시한다. 소음과 냄새, 공포감, 주차난은 거리에서 자동 추론하지 않는다.
경로가 없다는 결과도 “실제로 갈 수 없음”과 “데이터상 통행 가능 경로를 확인하지 못함”으로 구분한다. 미확인 링크를 억지로 연결하지 않고 현장 확인 과제로 남긴다.
# 8 학교와 생활 시설
초·중·고등학교, 대학교, 직장 목적지, 어린이집, 마트, 편의점, 전통시장, 약국, 병원, 공원, 버스 정류장, 지하철을 종류별로 필터링한다. 단순 시설 개수와 실제 이용 가능한 시설 개수는 다를 수 있으므로 운영 상태, 출입 시간, 이용 자격과 수집 범위를 관리한다.
학교는 정문까지의 거리·횡단·보도 단절을 체험하게 한다. 가까운 초등학교가 실제 배정학교라는 뜻은 아니다. 학교 위치와 통학구역·배정 규칙은 별도 출처 및 학년도로 보관하며, 중학교와 고등학교를 초등학교 통학구역과 같은 규칙으로 처리하지 않는다. 미확인 배정은 “확인 필요”로 표시한다.
지하철은 지상 입구, 엘리베이터, 대합실, 개찰구, 승강장 연결을 단계적으로 표현한다. 서울교통공사 데이터는 해당 운영기관의 범위를 확인하고, 코레일 등 다른 운영기관 구간을 포함했다고 가정하지 않는다. 현재 엘리베이터 고장 여부는 설치 목록만으로 판단하지 않는다. [S05][S06]
마트는 지도상 건물 외벽이 아니라 실제 출입문을 목적지로 삼고 운영일·영업 상태는 기준 날짜를 표시한다. 주변 시설 밀도는 수집한 범위에서만 집계하며 누락이 많은 단지를 시설 부족으로 단정하지 않는다.
# 9 신축 커뮤니티와 지하 체험
수영장, 피트니스, 작은 도서관, 독서실, 게스트하우스, 골프 연습장, 사우나, 돌봄 공간 등은 단지별 실제 존재 여부가 확인된 항목만 목록에 넣는다. 분양 시 계획, 준공 시설, 현재 운영 중인 시설을 분리한다. 관리비 포함 여부, 별도 요금, 예약, 외부인 이용 가능 여부, 휴관은 각각 자료가 있는 범위에서 보여준다.
실내 표현 수준은 세 가지다. 공개 도면과 이용 권한이 있는 공간은 실제 배치에 근거해 재현한다. 시설의 존재만 확인된 공간은 개념 재현이라고 표시하고 범용 실내를 사용한다. 자료가 없는 공간은 닫힌 문과 “내부 정보 준비 중”을 보여준다. 광고나 건설사 홍보 이미지의 존재만으로 현재 누구나 이용할 수 있다고 표시하지 않는다.
지하 주차장은 지상 진입, 차단기, 램프, 주차, 동 엘리베이터, 지상 복귀가 이어지는 생활 동선에 집중한다. 층고와 차량 진입 제한, 동 간 연결, 방문 차량 조건은 검수된 정보를 쓴다. 감시 사각지대, 통제 장치의 우회법 등은 임장 정보 범위에 포함하지 않는다.
# 10 혼자와 함께 하는 임장
1인 모드는 조용한 자유 탐색과 개인 체크리스트가 중심이다. 커플 모드는 각자의 우선순위를 먼저 고르고 같은 길을 함께 걷거나 분기해 본 뒤 의견을 비교한다. 가족 모드는 유모차, 아이 동반, 짐 들기, 엘리베이터 의존 같은 생활 조건을 조합한다. 가족 캐릭터는 시뮬레이션 프리셋이며 실제 아동 이름·학교·생활 일정을 요구하지 않는다.
공개 방은 같은 장면의 실제 접속자를 보여주고 기본 정원은 16명으로 제안한다. 개인 방은 초대 기반 최대 6명을 기본으로 한다. 정원은 서버 성능 측정 후 조정한다. 방이 나뉘어도 이용자는 같은 서울 월드에 있다는 느낌을 받지만 모든 이용자를 한 서버 좌표에 유지하지 않는다.
핀 찍기, 따라가기 동의, 길 공유, 간단한 이모트, 파티 메모를 먼저 만든다. 공개 채팅은 신고·차단·속도 제한과 운영 도구를 함께 만든 뒤 연다. 음성 채팅과 낯선 사람에게 보내는 무제한 쪽지는 후순위다. NPC는 NPC라고 표시하고 봇으로 접속자 수나 광고 노출을 부풀리지 않는다.
공동 노트에는 “거리와 시설 사실”, “나의 느낌”, “상대의 느낌”을 구분한다. 함께 본 화면과 경로 버전은 남기되 다른 사람의 실제 집 주소, 검색 이력, 자금 상황은 공개하지 않는다. 광고를 보는 동안에는 해당 플레이어만 대기 상태가 되고 나머지 방의 플레이가 멈추지 않아야 한다.
# 11 후기와 최근 이슈를 월드에 반영하는 방법
“초등학교가 정말 가깝다”는 표현은 정문까지의 경로와 횡단 횟수로 구체화한다. “커뮤니티가 좋다”는 시설 종류·운영 조건이라는 사실과 만족도라는 후기로 나눈다. “도로가 좁다”는 정확한 도로 구간과 방향별 차로 수·보도 폭·병목 위치로 나눈다. “해충을 봤다”는 특정 시점과 장소에 대한 제보로 저장하며 단지 전체의 상시 상태로 확대하지 않는다.
해충과 위생, 구조 결함처럼 오해의 영향이 큰 사안은 기본 월드에서 돌아다니는 벌레나 무너지는 벽으로 연출하지 않는다. 근거를 검수한 정보 서랍에서 기간·공간 범위·현재 확인 여부·해결 공지를 함께 제시한다. 입주민의 반대 경험도 별도 근거로 남기고, 해결된 이슈는 종료 상태로 전환한다.
## 이문과 휘경의 도로 사례
이문·휘경뉴타운과 회기역 일대를 하나의 장소로 합쳐 “2차선”이라고 기록하면 실제 도로 모델이 틀릴 수 있다. 차로 수에는 편도인지 왕복인지, 어디서 어디까지인지, 어느 날짜인지가 필요하다.
동대문구의 2025년 12월 8일 답변에는 당시 이문3구역 아파트 부분 준공과 도로 개선공사 미완료, 가능한 구간의 차로 증대 계획이 설명돼 있다. 2026년 6월 12일 답변은 이문3·4구역 지하차도 사업과 주민 의견 검토 절차를 설명한다. 이 자료들은 각각 당시 상태와 절차의 근거이며 2026년 10월 현재 공사 완료나 특정 구간의 실제 통행 상태를 입증하지 않는다. [S11][S12]
따라서 월드에는 “현재 도로”, “과거 기록”, “예정 사업” 레이어를 나누고 검수한 현재 도로만 기본 경로 계산에 사용한다. 개통 계획을 현재 경로로 연결하지 않는다. 공사 민원은 우려가 제기됐다는 사실과 민원 본문 주장 자체를 구분한다.
# 12 데이터의 수집과 검수
서울시 공동주택 정보는 단지 마스터의 출발점으로 사용할 수 있다. 공식 설명에는 일부 법정동 주소의 부정확성 안내가 있어 도로명주소와 건물·필지 식별자를 교차 확인해야 한다. 서울시 도보 네트워크는 유용한 초기 그래프지만 설명에 2020년 기준이 명시돼 있다. 갱신 표시에 최근 날짜가 보인다는 이유로 현재 신축 단지의 출입구까지 확인됐다고 간주하지 않는다. [S01][S02]
Aside는 사용자가 접근할 수 있는 페이지에서 허용된 범위의 정보를 읽고 표준 레코드로 정리하는 수집 인터페이스로 사용한다. 호갱노노와 커뮤니티의 사실 요약을 무조건 재배포할 수 있다는 전제를 두지 않는다. 서비스별 이용 조건, 자동 수집 허용 여부, 사진과 원문 이용 권한을 기록한다. 로그인 우회, CAPTCHA 우회, 비공개 커뮤니티 접근, 원문 대량 복제는 수집 설계에서 제외한다.
수집 파이프라인은 원천 등록, 위치·단지 식별, 관찰 단위 추출, 중복 묶기, 상충 근거 대조, 검수, 월드 연결, 배포 순서다. 원문을 붙여 넣은 즉시 게임 상태를 바꾸지 않는다. 복사된 기사나 같은 사람의 여러 게시글은 독립된 제보 여러 개로 계산하지 않는다. AI 네 개가 같은 문장을 반복해도 독립된 근거 하나가 늘어난 것으로 보지 않는다.
각 사실에는 무엇을 말하는지, 어느 공간인지, 관찰·게시·수집 날짜, 원본 URL, 사용 허가, 검수 상태, 적용 기간을 저장한다. 자료가 없는 값은 0이나 false로 채우지 않고 null 또는 unknown으로 남긴다. 신뢰도는 자의적인 93% 숫자 대신 출처 유형·시점·공간 특정성·독립성·검수 상태로 설명한다.
도로와 출입구를 수정하면 해당 경로 그래프와 관련 캐시만 갱신한다. 변경 전후 화면을 편집기에서 비교하고 검수자가 승인한 콘텐츠 버전을 배포한다. 잘못된 변경은 이전 버전으로 되돌릴 수 있어야 한다. 상업 광고가 있는 서비스이므로 공공 데이터도 데이터셋별 상업 이용·변형·재배포·출처표시 조건을 확인한다.
# 13 무료 운영과 광고 수익
광고는 월드의 가상 게시판, 동네 상가 안내판, 서울 지도 스폰서 영역, 접속과 지역 이동의 자연스러운 중단 지점에 배치한다. 실제 도로 위에 존재하는 광고판이라는 오해를 피하도록 가상 광고 시설임을 표시한다. 단지 정문이나 학교 표지를 광고 클릭 영역으로 바꾸지 않는다.
직접 계약한 월드 광고와 광고망이 제공하는 광고는 서로 다른 구현과 계약을 가진다. 자체 스폰서의 승인된 이미지·문구는 가상 광고판 텍스처로 제공할 수 있도록 설계한다. 일반 배너 광고 코드를 캡처해 3D 면에 붙이는 방식은 사용하지 않는다. 접속·전환 광고는 승인된 HTML5 게임용 광고 형식을 연동한다. Google의 Ad Placement API는 시작·전환·선택형 보상 광고 기회를 제공하지만 실제 광고 노출과 이용 가능 여부는 공급·빈도·계정 조건에 따라 달라진다. [A01][A02]
초기 노출 설정은 접속 시 하루 최대 1회, 접속과 전환을 합쳐 세션당 전면 광고 최대 2회, 전면 광고 간 최소 10분을 시험안으로 둔다. 이전 노출이 없는 첫 접속 광고에는 간격 검사를 적용하지 않는다. 첫 방문의 첫 이동, 길을 건너는 조작 중, 시설 정보 확인 중에는 전면 광고를 띄우지 않는다. 광고망의 정책과 승인 조건이 이 설정보다 엄격하면 그 조건을 따른다. [A03][A04]
광고가 없거나 차단되거나 로딩에 실패해도 임장은 계속된다. 선택형 보상 광고를 추가할 때 보상은 장식용 소품 정도로 제한하고 단지 정보를 열람하거나 더 정확한 경로를 보기 위해 광고 시청을 강제하지 않는다. 개인별 가족 구성·주거 예산·저장 주소 대신 현재 보고 있는 구와 장면 같은 문맥을 우선 사용한다.
## 광고 수입의 가정
월 광고 수입은 DAU × 하루 세션 수 × 30일 × 세션당 광고 기회 × 정산 가능한 유효 노출 비율 × 순 eCPM ÷ 1,000으로 추정한다. 유효 노출 비율에는 광고 공급 부족·차단·보이지 않은 노출·무효 트래픽을 포함한다. 이미 실제 유효 노출을 입력하는 계산에서는 이 비율을 다시 곱하지 않는다.
하루 1.5세션, 세션당 3기회, 유효 노출 비율 70%, 정산 후 eCPM 2,000원이라는 가정을 쓰면 다음과 같다. DAU는 해당 월의 일평균 이용자 수이며 순 eCPM은 해당 인벤토리 조합의 정산 노출 가중 평균이다. 3기회는 시작·전환·승인된 결과 페이지 등을 합한 평균 광고 기회이며 전면 광고 횟수가 아니다. 이는 한국 시장 단가 조사나 수입 보장이 아니라 민감도를 보기 위한 계산이다.
| DAU | 월 정산 대상 노출 가정 | 월 광고 수입 가정 |
|---|---|---|
| 300명 | 28,350회 | 56,700원 |
| 1,000명 | 94,500회 | 189,000원 |
| 5,000명 | 472,500회 | 945,000원 |
| 10,000명 | 945,000회 | 1,890,000원 |

같은 가정에서 현금 운영비가 월 100만원이면 광고망 수입만으로 충당하려면 약 5,300 DAU가 필요하다. 운영자의 개발·검수 노동, 신규 단지 제작, 영업과 세금까지 포함한 손익분기점은 더 높다. 광고 노출을 늘리기보다 작은 지역의 실제 관심 이용자를 확보하고 지역 업체와 직접 스폰서를 시험하는 전략을 제안한다. 직접 스폰서 수입은 위 광고망 수입과 같은 노출을 중복 계산하지 않고 별도 계약 항목으로 관리한다.

개발자 1명과 AI 도구를 전제로 한 계획 추정은 M0 약 1~2주, M1 추가 2~4주, M2 추가 4~8주다. 25구의 지리 검수와 콘텐츠 제작은 별도 작업량이며 권한 확보와 원천 품질에 따라 수개월 이상 달라질 수 있다. 이 일정은 견적이나 납기 약속이 아니다. 첫 실제 단지 1개의 제작시간을 측정한 뒤 나머지 단지 수에 적용해 다시 산정한다.
# 15 파일럿과 25구 후보
초기 실제 단지는 중구 래미안신당하이베르, 성동구 센트라스, 동대문구 래미안라그란데를 후보로 제안한다. 공식 이름과 검색 별칭을 함께 관리한다. 신당·왕십리·이문권을 비교하면 데이터 수집 동선을 묶으면서 다른 생활권 체험을 만들 수 있다. 이는 제작 편의와 체험 다양성을 위한 선정이며 투자 추천이나 단지 품질 순위가 아니다. 실제 경사·시설·최근 도로 상태는 이 선정만으로 확정하지 않는다.
구별 후보 전체와 공식 이름 확인 근거는 data/district_candidates.json 및 07_DISTRICT_PLAN.md에 있다. 자치구마다 “유명한 곳 한 개”를 영구 대표로 고정하지 않는다. 확장 시 건축 시기, 평지와 경사, 규모, 지하철 연결, 생활 편의, 데이터 이용권을 기준으로 각 구 안에서도 비교쌍을 늘린다.

# 17 운영과 성공 판단
첫 검증은 잠재 사용자 10~15명 정도를 대상으로 계획한다. 1인·커플·가족 설정을 고르게 포함하고, “동에서 역까지 가보기”, “유모차로 학교에 가보기”, “지하 주차 후 집으로 가보기” 같은 과제를 관찰한다. 표본이 작은 탐색 조사 결과를 시장 전체의 수요 통계로 쓰지 않는다.
핵심 지표는 생활 동선 체험 완료, 실제 도움이 된 발견, 비교 노트 저장, 실제 임장 준비로 이어진 비율이다. 광고는 순매출·실제 유효 노출과 함께 광고 직후 이탈·재방문·로드 지연을 본다. 초기 목표로 과제 완료 70% 이상, 중요한 경로 오류 0건을 두고 검증 후 조정한다. 광고 실험에서 이탈이 늘면 광고 기회 수를 줄인다.
상시 운영에는 신규 데이터 수집, 출처 권한 확인, 도로·시설 변경 검수, 이용자 제보 처리, 광고 소재 검토, 서버 관측이 포함된다. 25구 규모에서 사람의 검수와 자산 제작 시간이 서버비보다 커질 수 있으므로 단지 한 개를 추가하는 실제 작업시간과 갱신비를 측정한다.
네 개 AI의 제안을 합칠 때는 사용자 요구, 사실 근거, 구현 가능성, 비용, 테스트 결과 순으로 판단한다. 기능을 전부 합산해 첫 출시 범위를 불리는 대신 요구사항 ID별로 하나의 채택안을 정하고 다른 안은 결정 기록에 남긴다. 최종 구현의 첫 산출물은 M0의 움직이는 가상 동네, 경로 차이, 정보 근거, 모의 광고이며 이후 실제 단지로 교체한다.
# 18 기술과 배포의 기준
## 권장 기술 스택
웹 프런트는 Vite·React·TypeScript, 월드는 Three.js와 React Three Fiber를 기본안으로 제안한다. 정투영 카메라는 거리 때문에 물체 크기가 작아지는 원근 변화를 없애 미니어처 화면에 적합하다. 반복 건물·창문·나무의 자원 재사용과 단계별 상세도는 기기 성능을 관리하는 수단이다. 라이브러리의 실제 호환 버전은 구현 시작 시 확인하고 잠금 파일로 고정한다. [T1][T2][T14]

|---|---|---|

## PC·모바일·앱 확장
처음부터 PC 브라우저와 모바일 브라우저에 같은 앱을 제공한다. PC는 클릭·키보드 이동과 측면 정보 서랍, 모바일은 터치 목적지 지정·가상 조이스틱·하단 시트를 쓴다. 화면 크기에 따라 지형·사실·경로는 같게 유지하고 그림자·소품 밀도·해상도만 낮춘다. iOS Safari와 Android Chrome에서 직접 조작을 검수한다.
PWA는 M2에서 설치 경험과 이미 받은 앱·정적 장면의 캐시를 보강한다. 오프라인에서 현재 도로 상태나 다른 사용자의 위치를 최신처럼 보여주지 않는다. 앱스토어 유통이 필요해지면 Capacitor로 웹 기반 앱을 패키징하는 경로를 검토하되 네이티브 광고 SDK·권한·심사·터치 성능을 별도 검수한다. PWA를 만들었다고 앱스토어 등록이나 모바일 성능이 자동 완료되는 것은 아니다. [T13][T15]
## 데이터와 서버 배포
현실 좌표와 사실은 PostgreSQL·PostGIS와 콘텐츠 저장소에 두고, 길찾기 서비스는 검수한 다층 그래프를 계산한다. 게임 클라이언트는 결과를 캐릭터와 경로로 보여준다. 방 서버는 동행자의 입력·위치·장면·층을 검증하고 동기화한다. Colyseus는 서버가 상태를 변경하고 클라이언트에 변경분을 전달하는 구조의 후보다. 초기에 경로 계산이나 아바타 이동마다 LLM을 호출하지 않는다. [T7]
프런트와 GLB·텍스처는 CDN으로 배포하고, 일반 API와 실시간 방은 각자의 실행 환경에서 운영한다. 실시간 방의 메모리 상태를 요청이 끝나면 종료하는 함수에 의존시키지 않는다. 단독 탐색은 로컬 장면과 HTTP 조회로 동작하고 동행 때만 방에 연결한다. 초기에는 한 배포 지역과 소수 프로세스로 시작하며 분산 룸·캐시를 실제 병목이 생길 때 추가한다.
원천 자료, 근거 레코드, 경로 그래프, 시각 장면, 광고 배치를 서로 다른 책임으로 나누되 한 릴리스에서 호환되는 버전을 함께 배포한다. 광고 정보는 광고 서비스가 관리하고 경로와 후기의 원장을 수정하지 못한다. 연결이 불가능한 경우나 광고 공급이 없는 경우를 정상적인 상태로 처리한다.
PC 60fps, 모바일 낮은 사양 모드 30fps는 측정할 목표다. 초기 장면 압축 전송량 약 10MB 이하, 장면 이동 후 메모리 회수, 공개 방 16명에서 입력 동기화 등을 목표 장치에서 검증한다. 이 수치는 달성한 벤치마크가 아니다. 처음부터 복잡한 실시간 물리·교통 시뮬레이션·대규모 음성 대화·전 서울 상시 렌더를 한꺼번에 넣지 않는다.
# 19 사용자 확보와 재방문
초기 공개 콘텐츠는 “같은 단지에서 도보와 유모차 길이 어떻게 달라지는지”, “주차 후 동까지 얼마나 이동하는지”, “커플이 서로 다르게 본 장단점”처럼 체험 가치가 바로 드러나는 형식으로 만든다. 실제 게임 화면의 짧은 재생과 링크로 해당 경로를 열게 하고 가상 이미지와 실행 영상을 구분한다.
각 상세 단지에는 출처와 확인 날짜가 있는 공개 설명 페이지를 제공하고, 지도는 그 정보를 체험하는 진입점이 된다. 개인 메모와 실제 주소·자금 설정은 공개 검색에 노출하지 않는다. 얕은 자동 수집 문서를 대량 생성하기보다 처음 완성한 단지의 경로·시설·근거를 충실하게 설명한다.
재방문은 저장한 동네의 변경 확인, 친구 초대, 서로 다른 생활 설정 비교, 실제 임장 코스 준비에서 만든다. 25구 방문 스탬프나 장식 소품은 보조 재미로 제공할 수 있다. 보상 때문에 광고 앞을 반복 통과하거나 광고를 클릭하도록 유도하지 않는다.

## 한 번에 넘기는 작업 순서
이 패키지를 네 도구에 공통 자료로 제공한다. 다른 도구의 결과를 받은 파일만 별도로 보관한다.
06_MERGE_PROTOCOL.md의 통합 프롬프트로 MASTER_PRD, 결정 기록, 요구사항 비교표, 계약 변경, 개발 백로그를 만든다.
채택안을 코드 에이전트 한 세션이 통합 관리하고, 05_BUILD_PROMPTS.md의 M0 프롬프트를 실행한다.
M0의 가상 동네를 실제로 움직여 검수한 뒤, M1의 한 단지와 5개 실제 여정으로 확장한다.
## 실제로 검증한 범위
JSON Schema Draft 2020-12 구조와 가상 fixture의 참조·통행·다층 연결·근거·광고 권리 조건을 검사했다. 자동 사례 11개가 통과했고 오류 fixture 5개는 예상 단계에서 거부했다. 앱의 렌더링·터치 조작·실시간 동행·광고 제공자·기기 성능은 미실행으로 검증 보고서에 남겼다.
가상 월드는 18개 노드와 18개 링크를 포함한다. 설명용 자료의 도보·유모차 경로는 데이터 규칙을 검증하기 위한 값이며 실제 서울 거리로 사용할 수 없다. 단지 팩·공유 POI·원거리 통근 메타데이터의 추가 운영 계약은 구현 단계에서 버전과 함께 확장한다.
